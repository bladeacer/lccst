# Benchmarking Evaluation Speed: Findings

## Problem

After the harness exits during `make benchmark-free`, the evaluation pipeline
(settle + report + cleanup) takes longer than expected. This document records
the investigation and the optimisations applied.

## Evaluation Pipeline

After the harness exits, `benchmark-run` executes three sequential steps:

1. `telemetry-settle` — settles phase token counts from the host store.
2. `run_benchmark.py --install-deps` — runs install + tests for 6 variants,
   generates a markdown report.
3. `bench-cleanup` + `bench-update` — removes the workspace, regenerates
   README tables.

## Measured Timings

All measurements taken on the benchmark machine (Node.js 22, Go 1.27.2,
pnpm 12.14.0, uv 0.5.9, tiktoken not in system Python).

### telemetry-settle (settle.js)

- `resolveStoreCandidates()` called once per phase (6 times for 6 phases):
  8.5 ms total for 6 calls. Fast.
- Full settle for 2 phases (measured on live workspace): 86 ms.
- `resolveStoreCandidates` scans `~/.local/share` for `.db` files, tests
  each with `isSqliteFile` (reads 16-byte SQLite header). Only 5 valid
  candidates found. Fast.
- Each phase's `readTurnUsage` opens candidate SQLite stores via `DatabaseSync`,
  checks schema, queries sessions. ~40 ms per phase.
- **Verdict**: not a bottleneck. ~250 ms for 6 phases.

### run_benchmark.py — rerun_with_uv double-process (verified)

**With warm caches** (venv already synced, packages installed):

| Invocation method | Total time | Parent overhead |
|---|---|---|
| `python3 run_benchmark.py` (current) | 4.193 s | ~80 ms |
| `uv run python3 run_benchmark.py` (direct) | 4.112 s | ~0 ms |

The parent process overhead is only ~80 ms with warm caches. On a cold cache
(first run, or `.venv` deleted), the `uv run` inside `rerun_with_uv` must
install `tiktoken` (a Rust extension), adding 10-30+ seconds.

### run_benchmark.py — per-step timing (warm caches, test workspace)

Measured by running each install + test command individually:

| Step | Time |
|---|---|
| Install python (uv sync) x2 | 0.012 s + 0.008 s = 0.020 s |
| Install react (pnpm install) x2 | 0.011 s + 0.017 s = 0.028 s |
| Install go (go mod download) x2 | 0.004 s + 0.004 s = 0.008 s |
| Test python (pytest) x2 | 0.287 s + 0.814 s = 1.101 s |
| Test react (jest) x2 | 0.541 s + 0.542 s = 1.083 s |
| Test go (go test) x2 | 0.035 s + 0.049 s = 0.084 s |
| detect_harness_version("kilo") | **1.360 s** |
| detect_tool_versions() 21 ms | 0.024 s |
| **Subtotal** | **~2.7 s** |
| Python startup + tiktoken import + report gen | ~0.5 s |
| **Total** | **~4.1 s** |

Install commands are negligible (0.056 s total). Test execution is ~2.3 s.
The **single most expensive operation is `detect_harness_version`** at 1.36 s
(33% of the evaluation). This runs `kilo --version`, a Node.js CLI invocation.

### run_benchmark.py — detect_harness_version

`generate_markdown` calls `detect_harness_version(harness)` in `main()`:
- `kilo --version`: 1349 ms (Node.js CLI startup).
- `opencode --version`: 255 ms.
- **Verdict**: 1.3 s for kilo. Called once, but significant as it blocks
  report generation.

### run_benchmark.py — detect_tool_versions (inside generate_markdown)

- `python3 --version` + `pnpm --version` + `go version`: 21 ms total.
- Called inside `generate_markdown()` (line 753). `detect_harness_version()`
  is called in `main()` (line 923) and its result passed as an argument.
- **Verdict**: negligible.

### run_benchmark.py — collect_results (install + test)

Per variant (measured on existing completed variants):

| Variant | Install | Test | Total |
|---|---|---|---|
| python-http-server | `uv sync` | `uv run python3 -m pytest` | 5.3 s |
| react-timer | `pnpm install --no-frozen-lockfile` | `npx --no-install jest` | 0.4 s |
| go-login-crud | `go mod download` | `go test ./tests/ -v` | not measured |

- `uv sync` (venv already exists): 11 ms.
- `pnpm install --no-frozen-lockfile` (warm store): 12 ms.
- `pytest` (10 tests, warm venv): 5.29 s.
- `jest` (no tests found in partial workspace): 0.42 s.
- **Verdict**: install commands are fast with warm caches. pytest dominates
  (~5 s per python variant). 6 variants sequentially = ~15-25 s.

### update_readme_benchmarks.py (bench-update)

- Scans 13 existing benchmark report dirs, parses markdown, generates tables:
  88 ms.
- `kilo --version` called again inside `detect_tool_versions` of
  `update_readme_benchmarks.py`? No — `update_readme_benchmarks.py` does NOT
  call `detect_harness_version`. It parses existing reports.
- **Verdict**: not a bottleneck.

### bench-cleanup workspace removal

- `rm -rf "$(BENCH_WORKSPACE)"`: depends on workspace size. If the model
  created large `node_modules`/`.venv` directories, removal could take
  several seconds. Not measured but potentially slow for large workspaces.

## Identified Inefficiencies

### 1. Parent process in `rerun_with_uv` is completely wasted

The Makefile calls `python3` (system) which always fails to import tiktoken.
The parent then spawns `uv run python3` which does all the real work.
The parent's Python startup, import attempt, and process spawn are pure waste.

**Fix**: Call `uv run python3` directly in the Makefile `bench-report` target.
The script starts in the uv environment with tiktoken, so `rerun_with_uv()`
is never triggered.

### 2. `detect_harness_version("kilo")` takes 1.3 seconds

Called once per evaluation. `kilo --version` starts a Node.js CLI which is
slow. The Makefile already runs `$(HARNESS) --version` in `benchmark-run`
for display purposes before the harness starts. This version is not passed
to `run_benchmark.py`.

**Fix**: Pass the harness version from the Makefile to `run_benchmark.py`
via a `--harness-version` argument, skipping the redundant CLI call.

> We also need to test that this works for detecting harness version for
opencode as well.

### 3. `resolveStoreCandidates()` called once per phase in settle

`settle.ts` calls `readTurnUsage()` for each phase. Since `query.candidates`
is not passed, `readTurnUsage()` calls `resolveStoreCandidates()` each time
(6 times for 6 phases). Each call rescans `~/.local/share` for `.db` files.

While the total is only 8.5 ms, it is redundant work. The candidates do not
change between phases.

**Fix**: Resolve candidates once in `settle.ts` and pass to `readTurnUsage`.

### 4. `readTurnUsage` reopens candidate stores per phase

For each phase, `readTurnUsage` iterates through all candidate stores,
opening each SQLite database with `DatabaseSync`, checking the schema, and
querying for sessions. Once the correct store is found for phase N, phases
N+1 through 6 repeat the same candidate iteration.

**Fix**: Cache the resolved store (the one matching the workspace directory)
and reuse its `DatabaseSync` handle for all phases.

### 5. Redundant `uv sync` for Python variants

The Python install command is `["uv", "sync"]`. The test command is
`["uv", "run", "python3", "-m", "pytest", ...]`. `uv run` automatically
syncs the environment, making the explicit `uv sync` redundant.

**Fix**: Skip the install step for projects where the test command self-syncs
(`uv run`, `go test`). Keep `pnpm install` for React since `npx --no-install`
requires it.

### 6. Python benchmark environment not pre-synced

The Makefile calls `python3 run_benchmark.py` which triggers `rerun_with_uv`.
That function spawns `uv run python3`, which reads `playground/benchmarks/
pyproject.toml` (declares `tiktoken>=0.7`) and `uv.lock`.

- `uv.lock` IS tracked in git (committed).
- `.venv` is NOT tracked (`.venv` is in `.gitignore`). No Makefile target
  creates it. `telemetry-build` only runs `pnpm install` + `pnpm run build`
  for the TypeScript MCP server.

So on a fresh machine or after `.venv` deletion, the first `uv run` inside
`rerun_with_uv` must create the venv and install tiktoken (a Rust extension).
This can take 10-30+ seconds depending on network and cache warmth.

Even when the venv already exists, `uv run` still needs to check the lockfile
and verify the environment, adding ~50 ms per invocation.

**Fix**: Pre-sync the Python environment in `telemetry-build` (or
`benchmark-free`) by running `uv sync` in `playground/benchmarks/`. This
ensures the venv is ready before `run_benchmark.py` is called, and enables
the Makefile to call `uv run python3` directly (finding tiktoken already
installed).

## Summary of Planned Changes

1. **Makefile** (`bench-report`): Replace `python3` with `uv run python3`
   (via `cd $(BENCH_DIR) && uv run python3 run_benchmark.py`), with a
   fallback to bare `python3` when `uv` is absent. Eliminates the wasted
   parent process that always fails to import tiktoken.
2. **Makefile** (`telemetry-build`): Add `uv sync` so the benchmark Python
   environment (with `tiktoken`) is pre-synced before any run. Eliminates
   first-run `uv run` sync delay.
3. **settle.ts**: Resolve store candidates once via `resolveStoreCandidates()`,
   pass the cached list to all `readTurnUsage()` calls. Eliminates 5 redundant
   filesystem scans.
4. **settle.ts**: Once the matching store is found, cache its `DatabaseSync`
   handle and reuse for subsequent phases. Eliminates repeated database opens.
5. **run_benchmark.py**: Add `--harness-version` CLI argument. The Makefile
   captures `$(HARNESS) --version` output (already run for display in
   `benchmark-run`) and passes it, skipping the 1.3 s `kilo --version` call.
6. **run_benchmark.py**: Skip redundant install for projects whose test command
   self-manages dependencies (`uv run` for Python, `go test` for Go). Keep
   `pnpm install --no-frozen-lockfile` for React since `npx --no-install`
   requires it. This removes 2 redundant `uv sync` calls and 2 redundant
   `go mod download` calls.

None of these change the file filter, test commands, or scoring rubric.
