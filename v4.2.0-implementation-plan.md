# LCCST 4.2.0 Implementation Plan

## Purpose

This document records the audit findings after version 4.1.0 and the
implementation plan for version 4.2.0. The findings cover the skill
(`SKILL.md`), the user-facing claims (`README.md`), the benchmark prompts
(`playground/agent-prompt.md`, `playground/guide.md`, `playground/traps.md`),
and the tooling (`src/index.ts`, the telemetry MCP, the Makefile, and the
benchmark scanner).

The plan fixes the findings in dependency order. Measurement validity comes
first, because every later comparison depends on numbers that can be trusted.

## Context: what 4.1.0 changed and why it did not help

Version 4.1.0 made task-runner detection declaration-based and added four
weak-model safety rules to the skill. The benchmark results did not improve:

- Weaker models still failed to complete runs. The report directories for
  `cohere-north-mini-code-free`, `glm-5.3-flash-free`, and both
  `ling-3.0-flash-fin-free` runs hold no report at all. Minimax v4.1.0 needed
  73 model turns over 6 phases and 8.06M ART tokens. Its plain `react-timer`
  variant failed (`FAILED (code 1)`), as did mimo's plain `react-timer` in
  both the v3.8.0 and the v4.1.0 runs.
- Stronger models did not benefit either. Mimo's guided file-content token
  (FCT) overhead rose from +136% (v3.8.0) to +148% (v4.1.0). The two 4.1.0
  runs score near the bottom of the ranking on efficiency.

The audit found three structural causes. None of them was addressed by the
4.1.0 rules.

1. The benchmark let the guided variant copy the plain output. The best
   ranked run exploited this shortcut.
2. The scoring rubric saturates and then fights the skill's own deliverables.
3. The skill, the README, and the server state three different protocols in
   several places, so a model that reads all three sources receives
   conflicting instructions.

## Audit findings

### 1. Measurement validity

#### 1.1 The dots v4.0.0 run measured copying, not the skill

Both variants run in one harness session, plain first (`agent-prompt.md`
section 3). Nothing stops the model from copying the plain output into the
guided directory. The dots v4.0.0 report shows the copy:

- `react-timer`: plain and guided are identical. 3 files, 140 lines, 1025
  tokens in both columns.
- `go-login-crud`: plain and guided are identical. 4 files, 419 lines, 3004
  tokens in both columns.
- The guided ART breakdown for those phases shows 350 and 497 prompt tokens.
  The plain phases show 367,809 and 228,305. The guided phases did no real
  work.

Dots holds rank 1 in `model-ranking.md` with a -96% ART overhead and a
composite of 76.1. The composite rests on guided phases that copied the plain
output. The run is contaminated and must not set the baseline that later runs
compare against.

The 4.1.0 ladder rules removed the cheap path (no probe runs, no shell
switches, declaration checks), so a strong model now pays the full protocol
cost against a contaminated baseline. This explains the perceived regression
for stronger models.

#### 1.2 Per-phase token attribution is unreliable

Dots' python plain phase reports 777,683 prompt tokens while its guided phase
reports 1,033. No single phase of this size class should hold 777k prompt
tokens. The settle step reads a time span from the host store and can
mis-window a session. There is no sanity check, so a corrupted number flows
into the FCT and ART overhead terms and into the composite score.

The settle step also degrades silently. When a harness upgrade changes the
store schema, `settle.js` reports "no count" for a phase. The report then
presents a measurement failure as a valid zero. The rejection gate in
`update_readme_benchmarks.py` rejects such runs, but the report file is still
written and can be read as data.

#### 1.3 Python variants resolve dependencies at run time

The 4.1.0 evaluation optimisation removed the install step for python
variants, because `uv run` syncs on demand. A fresh variant directory holds
no lockfile, so `uv run` resolves dependency versions at run time. The plain
column and the guided column of one report can resolve different dependency
versions. The columns no longer measure the same environment.

### 2. Scoring and ranking

#### 2.1 The guided robustness term saturates

Every ranked run scores 100/100 average guided robustness. The term carries
40% of the composite and cannot discriminate between models. The ranking is
decided by the efficiency terms, which build on the token numbers that
section 1.2 shows to be unreliable.

#### 2.2 The rubric and the token penalty pull in opposite directions

The robustness rubric rewards detected features: typing, security, and error
handling (`run_benchmark.py`, `compute_robustness_score`). The skill's own
deliverables demand typed errors, boundary validation, docstrings, and
per-module tests. A model that follows the skill produces more code, earns
more rubric points, and then loses composite score to the token economy
penalty added in 4.0.0. The current design rewards bloat (mimo, minimax) or
shortcuts (dots). No path rewards the intended behaviour: a lean, correct,
test-verified implementation.

#### 2.3 The ranking mixes protocol versions

`model-ranking.md` ranks runs from v3.8.0, v4.0.0, and v4.1.0 in one table.
A version change alters the prompt and the rules, so the rows do not measure
the same protocol. The table states the version per row, but the composite
ranking ignores it.

### 3. Three-way parity gaps between SKILL.md, README.md, and the MCP server

All three sources claim one protocol. The command names do match: eleven
slash commands in the skill map to eleven registered tools, and the README
states the 1:1 mapping. The behaviour does not match. The concrete gaps:

#### 3.1 Lint commands per manifest

- `SKILL.md`: the manifest table has Test, Format, and Build columns. No lint
  column, although `/lint` is a command.
- `README.md`: the ladder snippet lists only test commands per manifest.
- `src/index.ts`: `MANIFEST_PRIORITY` holds `uv run ruff check`,
  `cargo clippy`, `go vet ./...`, and `pnpm run lint`.

A model in Bare Skill Mode has no documented lint command per manifest. The
server knows one. The README shows none.

#### 3.2 Scripts fallback surface

- `SKILL.md`: names `scripts/<command>.sh`, `.py`, `.ts` only.
- `README.md`: names "`scripts/` helpers" only.
- `src/index.ts` `listShellScripts`: scans `scripts/`, `tools/`, `bin/`, and
  `script/`; accepts `.sh`, `.py`, `.js`, `.ts`, `.mjs`, `.cjs`, and any
  executable file; also matches the plural form (`tests` for `test`).

The server searches four times the documented surface.

#### 3.3 Argument availability

- `SKILL.md` frontmatter: one generic argument block (`command`, `path`,
  `mode`, `dry_run`, `abort`) that implies every argument on every command.
  The body names `--dry-run` and `--abort` for `/swarm`, and `--dry-run` for
  `/verify` only.
- `README.md`: documents `path` and `mode` (on the eight state-changing
  tools). Documents neither `dryRun` nor `abort`.
- `src/index.ts`: `abort` exists on `swarm` only. `dryRun` exists on `swarm`,
  `lint`, `format`, `test`, `build`, and `verify`. `mode` exists on `init`,
  `audit`, `swarm`, `lint`, `format`, `test`, `build`, and `verify`.

The README's `mode` list matches the code exactly. The skill's generic block
does not, and the README omits two arguments the server accepts.

#### 3.4 Hunk isolation and cluster semantics

- `SKILL.md`: the mandate says "Do not skip atomic hunk isolation". The
  terminology defines a cluster as "a group of changed hunks that belong to
  one domain".
- `README.md`: "Atomic hunk isolation ... are non-negotiable". "Locality
  Clustering groups diffs by domain so each atomic commit rolls back
  cleanly".
- `src/index.ts`: `clusterHunks` never inspects hunks. It extracts file names
  from `git diff --stat` lines and groups them by top-level directory.
  `clusterPaths` groups by the first path segment only.

Both documents promise hunk-level, domain-based clustering. The server
delivers top-level directory grouping. A model that trusts the documents
expects a plan the server cannot produce.

#### 3.5 Swarm completion and the state file

- `SKILL.md`: "A completed `/swarm` loop removes the state file after its
  final commit".
- `README.md`: silent on this point.
- `src/index.ts`: the server does not commit and never learns that the loop
  completed. Only `/verify` or `/swarm --abort` clears `.lccst/state.json`.

The documented lifecycle step is unreachable in host-tool mode.

#### 3.6 The envelope step field is inconsistent

`init`, `audit`, `swarm`, `tooling`, `verify`, `compliance`, and `version`
set the step field to `/init` style. Every reply of `runStepTool` (the
`lint`, `format`, `test`, and `build` tools) sets the bare name, for example
`test`. A client that switches on the step field sees two naming schemes.

#### 3.7 The swarm prompt over-promises

The registered `swarm` prompt describes itself as "Enforce deterministic
lint-cluster-split-test-commit boundaries". The server does not lint, does
not split, and does not commit. The README describes the prompt more
accurately as returning the SKILL.md content.

#### 3.8 /tooling omits the runners that /test uses

`SKILL.md` and `README.md` describe `/tooling` as listing Makefile targets,
scripts helpers, and package scripts. The server does the same. But
`resolveCommand` also consults `mise.toml`, `justfile`, and `Taskfile.yml`,
and neither `/init` nor `/tooling` surfaces those runners. A caller cannot
see which runner the next `/test` call will use.

### 4. Weak-model failure paths

The 4.1.0 safety rules treat symptoms. The structural failure paths remain.

#### 4.1 The telemetry protocol is a multi-step dance

`agent-prompt.md` section 4 requires all of the following: call the tool at
the phase end, expect a refusal when the manifest or directory is missing,
call again after the refusal, never apologise, state the result, keep the
call as the last tool operation, and end the response with one of three
exact state markers. Each requirement is a separate failure opportunity. A
weak model that violates one wastes a turn or a phase.

`checkPhase` refuses a call when the variant directory holds no manifest with
the expected name. A weak python model that writes `requirements.txt`
instead of `pyproject.toml` receives a refusal it cannot act on.

#### 4.2 The sandbox rules multiply refusal risk

`agent-prompt.md` section 2 demands a blind deletion pass over six
directories and forbids `ls`, `find`, `git status`, `git diff`, `git log`,
and `open`. A weak model that runs one forbidden command or deletes one
extra path breaks the run contract. The rules exist to protect the clean
room, but each rule is also a trap for the model under test.

#### 4.3 More skill text, more violation surface

Version 4.1.0 added roughly thirty lines of rules to `SKILL.md`. Every rule
is another way for a weak model to violate the protocol, and another unit of
ceremony for a strong model. The rules did not change any structural cause.

### 5. Tooling and telemetry flaws

#### 5.1 The MCP server runs project commands without a timeout

`runCommand` in `src/index.ts` calls `execFileSync` with no timeout. A
hanging test command hangs the server and the caller forever. The benchmark
scanner sets `TEST_TIMEOUT = 300`; the server sets nothing.

#### 5.2 The Makefile parser can report false targets

`readMakefile` trims each line and matches `name:`. A recipe line that looks
like `foo: bar` after trimming registers a false target. Comments and
line continuations are not handled beyond the basic checks.

#### 5.3 /audit writes state before it checks git

The `audit` tool writes `.lccst/state.json` and then runs `gitChanges`. A
non-git target keeps a state file behind after the error reply.

#### 5.4 The swarm prompt description drifts from the server

See section 3.7. The description is not derived from the tool behaviour, so
it drifts silently.

#### 5.5 The benchmark always exits zero

`benchmark-run` in the Makefile ends with `exit 0`. A failed harness, a
failed report step, and a clean run look identical to anything downstream.

#### 5.6 The declared toolchain is stale

`guide.md` and `DECLARED_TOOLCHAIN` in `run_benchmark.py` declare pnpm
11.3.0 and go 1.26.4-X. The machine runs pnpm 12.14.0 and go 1.27.2-X. Every
report now carries a drift note. A note that always appears carries no
information.

### 6. Benchmark prompt design

#### 6.1 One session holds both variants

See section 1.1. This is the single most damaging design flaw in the
benchmark.

#### 6.2 traps.md coaches the guided variant on scanner internals

`traps.md` tells the guided variant that the scanner counts `.tsx` files
only, that the workspace yaml needs a `packages` key, and that
`VIRTUAL_ENV` must be removed. The plain variant never sees these facts. The
guided column then measures access to answer keys, not the skill. Genuine
trap history (float drift, rate limiter, cached Go results) belongs to the
guided package; scanner constraints belong to both variants.

## Implementation plan

Each item is one commit, in this order. Commit messages and version bump
levels follow `AGENTS.md` and the version policy in `SKILL.md`. The levels
are cumulative: the sequence lands as a minor release 4.2.0, unless item 5
changes the argument surface or the reply envelope, which makes the release
major (5.0.0).

### Phase 1: measurement validity

#### Commit 1

`feat(bench): isolate benchmark variants into separate harness sessions`

Level: minor.

- `Makefile` `benchmark-run`: run one harness session per subproject-variant
  (six sessions). Seed the clean room once. Pass the subproject and the
  variant to each session through the task prompt, as the telemetry tool
  already names them.
- `playground/agent-prompt.md`: rewrite for a single-variant assignment.
  Remove "Implement plain first, then skill-guided". Remove the six-directory
  blind deletion pass, which exists only to clear the sibling variant.
- `scripts/benchmark-picker.ts`: pass `subproject` and `variant` values, as
  the prompt already anticipates ("If the host supplies a single `variant`
  value, implement only that value").

#### Commit 2

`feat(bench): reject contaminated and misattributed telemetry`

Level: patch.

- `settle.ts` or `run_benchmark.py`: flag a phase whose settled tokens exceed
  the session total. Flag a report whose guided file inventory equals the
  plain inventory exactly (identical file count, line count, and token
  count).
- `update_readme_benchmarks.py`: a flagged run does not enter the ranking
  table; `reject_reason` states the flag.
- Regenerate `model-ranking.md` with the dots v4.0.0 run marked contaminated.

#### Commit 3

`fix(bench): pin dependency resolution per variant`

Level: patch.

- `run_benchmark.py`: sync or pin dependencies once per variant directory
  before the test run, so the plain column and the guided column resolve
  identical versions. Restore the `uv sync` for python variants, or copy a
  committed lockfile into the variant directory before `uv run`.

### Phase 2: parity fixes

#### Commit 4

`fix(mcp): add command timeout and harden tooling discovery`

Level: minor.

- `runCommand`: add a timeout (default 300 s, `LCCST_COMMAND_TIMEOUT`
  override). A timed-out command reports its own exit state.
- `readMakefile`: ignore recipe lines (leading tab), comments, and line
  continuations before matching a target.
- `audit`: write `.lccst/state.json` only after `gitChanges` succeeds.
- `init` and `tooling`: surface the task runners that `resolveCommand`
  consults (`mise.toml`, `justfile`, `Taskfile.yml`), so the caller sees the
  runner that the next step will use.
- `runStepTool`: set the envelope step to `/lint`, `/format`, `/test`, and
  `/build`, matching every other tool.

#### Commit 5

`feat(skill): close skill-README-MCP parity gaps`

Level: minor, or major if the argument surface or the reply envelope changes.

One decision per gap: change the skill, change the README, or change the
server. The parity check in commit 9 then holds the three sources together.

- Lint column (section 3.1): add the lint commands to the `SKILL.md`
  manifest table and to the README ladder snippet, matching
  `MANIFEST_PRIORITY`.
- Scripts fallback (section 3.2): either document the full search surface in
  `SKILL.md` and the README (`scripts/`, `tools/`, `bin/`, `script/`;
  plural matching), or narrow `listShellScripts` to `scripts/`. Prefer the
  narrower server surface: the ladder must stay predictable.
- Arguments (section 3.3): document per-command availability. `abort` names
  `/swarm`. `dryRun` names `/swarm`, `/verify`, `/lint`, `/format`, `/test`,
  and `/build`. `mode` names the eight state-changing tools, as the README
  already states. The README gains the `dryRun` and `abort` lines.
- Hunk isolation (section 3.4): reword `SKILL.md` and the README. A cluster
  is a top-level group of changed files. Hunk-level isolation is the duty of
  the caller with `git add -p`, in Bare Skill Mode and in host-tool mode
  alike. The mandate keeps the requirement; the server does not claim it.
- State lifecycle (section 3.5): state that the caller clears the state file
  after the final commit, through `/verify` or `/swarm --abort`. The server
  never learns of the final commit.
- Swarm prompt (section 3.7): describe the prompt as returning the SKILL.md
  content for the active workspace, matching the README.

#### Commit 6

`feat(bench): rebalance the robustness rubric`

Level: minor.

- Stop giving 40% weight to a saturated term. Either add a bloat factor
  (lines per delivered feature) so the rubric discriminates, or shift the
  weight to the pass rate and to honest efficiency terms.
- Re-tune the token economy penalty. It must not punish the deliverables that
  the skill requires: docstrings, per-module tests, and typed errors. A lean
  compliant implementation must outscore both a bloated one and a copied one.

#### Commit 7

`feat(bench): move scanner facts to the shared guide and refresh prompts`

Level: patch.

- Move the scanner constraints from `traps.md` to `playground/guide.md`:
  `.tsx` counting, the pnpm workspace `packages` key, `uv run python3`, and
  the test-directory layouts. Both variants read `guide.md`. Trap history
  (float drift, rate limiter, cached Go results, email expression) stays in
  `traps.md` for the guided variant.
- Compress the telemetry section of `agent-prompt.md` to one recovery rule:
  a refused or early call records nothing; call the tool again at the true
  end of the phase; no apology, one state marker.
- Update `DECLARED_TOOLCHAIN` and the `guide.md` toolchain list to the
  current machine (pnpm 12.x, go 1.27.x), so the drift note carries
  information again.

#### Commit 8

`feat(skill): consolidate weak-model rules into a checklist`

Level: minor.

- Fold the 4.1.0 weak-model rule paragraphs in `SKILL.md` into one compact
  checklist with the same content: check files by path, treat a runner
  without the task as a skip, detect the platform once, fix a failing
  command instead of switching shells. Shorter text reduces violation surface
  for weak models and ceremony for strong ones.
- Test in Bare Skill Mode before committing, per the `SKILL.md` editing
  rules.

### Phase 3: the parity check

#### Commit 9

`feat(test): add three-way skill-README-MCP parity check`

Level: patch.

See the next section for the specification. Delete the stub `parityCheck()`
from `tests/init_handshake.test.ts` in the same commit.

### Phase 4: validation

#### Commit 10

`feat(bench): rerun strong and weak models on isolated sessions`

Level: patch.

- Re-run one strong model (dots) and one weak model (mimo or minimax) under
  the isolated-session design.
- Confirm that no guided phase duplicates its plain sibling, that every phase
  holds a settled count, and that both columns do real work.
- Regenerate `model-ranking.md` and the README tables. Mark pre-fix runs as
  non-comparable, or remove them from the ranking.

## The parity check specification

The check holds three sources to one protocol: `SKILL.md`, `README.md`, and
the MCP server in `src/index.ts`. Parity drift then fails `make test` instead
of surfacing in a benchmark run.

### The single source of truth

`src/index.ts` exports `PROTOCOL_COMMANDS`: one entry per registered tool,
with the tool name, the argument names it accepts, and one description line.
The registrations consume the same constant, so the constant cannot drift
from the tools themselves. The server version exports alongside it.

### The checks

1. Command-set parity. The `command` enum in the `SKILL.md` frontmatter, the
   section 3 command list, `PROTOCOL_COMMANDS`, and the README tool list all
   hold the same names, one entry each, no extras.
2. Argument parity. For each command, the arguments claimed in `SKILL.md`
   (body and frontmatter) and the arguments claimed in the README equal the
   arguments in `PROTOCOL_COMMANDS`. `abort` appears on `swarm` only.
   `dryRun` appears on `swarm`, `verify`, `lint`, `format`, `test`, and
   `build`. `mode` appears on the eight state-changing tools.
3. Ladder parity. Parse the manifest table and the task-runner table in
   `SKILL.md` and the ladder snippet in the README. Compare row order and
   commands with `MANIFEST_PRIORITY` and with the runner order in
   `resolveCommand`. The manifest table must hold a lint column.
4. Version parity. The `SKILL.md` metadata version, the `package.json`
   version, the server constant, the telemetry MCP version, and the handshake
   test all state one version.
5. Envelope parity. Every tool declares `ENVELOPE_OUTPUT_SCHEMA`. Every reply
   path returns the envelope. Every step field starts with `/`.

### The wiring

- `scripts/test-parity.ts` holds the checks. It imports `PROTOCOL_COMMANDS`
  from `src/index.ts`, reads `SKILL.md` and `README.md` as text, and parses
  the tables and the frontmatter.
- `make test_parity` runs the script. `make test` and the CI workflow run it
  after `test_swarm`.
- A failed check prints one line per gap: the source, the expected value, and
  the actual value.

## Version policy

The plan is one minor release, 4.2.0, with one patch-level or minor-level
commit per item. Run `pnpm run bump 4.2.0` after the last behaviour commit,
then `make build`. Write `docs/changelogs/lccst-4.2.0.md` with the sections
that this plan justifies: measurement validity, parity, scoring, and the
prompt diet. If commit 5 changes the argument surface or the reply envelope,
the release becomes 5.0.0 and the changelog must state the breaking change.
